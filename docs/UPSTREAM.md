# Upstream compatibility snapshot

Last researched: **2026-10-03**. Slice 0 and Slice 1 image manifests were resolved directly from their official registries. Newer Paperclip and Hermes releases exist, but the accepted Slice 1 pins remain deliberate until live acceptance because changing them would add database migrations and substantial runtime/configuration churn. This is not permission to skip revalidation: at the start of each later implementation slice, confirm the selected stable release, read its migration notes, and record the exact image/package digest in deployment configuration.

Only official documentation and official repositories are authoritative for implementation. Search results, blog posts, and this summary are navigation aids.

## Evidence and version-sensitive assumptions

### Paperclip

- The current stable release is [Paperclip v2026.1001.0](https://github.com/PaperclipAI/paperclip/releases/tag/v2026.1001.0) (2026-10-02), commit `8f8a0ab7effbd6a0584107d8038736c134ee5047`. Its GHCR multi-architecture digest is `sha256:08dbadebd4d40550eb336c25c3691f582322a88bae3f1cca101c5dd096bdc9d3`; linux/amd64 resolves to `sha256:8462fc831df840f44a324f961180efd09939a6df125e4486dc63cf33be90937e`. Moving from the deployed pin applies migrations 0280 through 0283 and changes defaults around unconfigured execution harnesses. Slice 1 does not use the removed legacy Composio integration. Keep `v2026.916.1` through Slice 1 live acceptance, then evaluate the upgrade as its own reviewed change.
- The deployed pinned release is [Paperclip v2026.916.1](https://github.com/PaperclipAI/paperclip/releases/tag/v2026.916.1), commit `d554c4789ed3930f8a53ac9fdf6503b3187097da`. It is a no-migration patch over `v2026.916.0`.
- The official registry publishes the stable image tag without a leading `v`: `2026.916.1`. The `v2026.916.1` image reference does not exist. Both `2026.916.1` and `sha-d554c47` resolved to the pinned multi-architecture digest recorded above on 2026-09-24.
- The [API overview](https://docs.paperclip.ing/reference/api/overview/) documents bearer-authenticated board and agent identities, `GET /api/health`, and a runtime OpenAPI document at `GET /api/openapi.json`.
- The [Hermes Gateway adapter](https://docs.paperclip.ing/reference/adapters/hermes-gateway/) is built in. It calls `POST /v1/runs`, follows SSE events with polling fallback, stops timed-out runs, and supports issue-scoped sessions.
- The official [Hermes Gateway onboarding guide](https://github.com/PaperclipAI/paperclip/blob/master/doc/HERMES_GATEWAY_ONBOARDING.md) distinguishes the Hermes inference key, Hermes API-server key, and claimed Paperclip agent key. These must remain separate.
- The adapter currently declares `supportsLocalAgentJwt: false` in the [official source](https://github.com/PaperclipAI/paperclip/blob/master/packages/adapters/hermes/src/gateway/index.ts). Therefore an always-on Hermes profile needs its own revocable Paperclip agent key for Telegram-originated and gateway-originated Paperclip calls. Slice 2 must run the upstream gateway E2E smoke rather than assuming callback auth works.
- The official [Paperclip MCP server](https://github.com/PaperclipAI/paperclip/tree/master/packages/mcp-server) is a thin wrapper over the REST API and exposes issue read/write, questions, confirmations, approvals, projects, and goals. Nix will tool-allowlist it instead of building a bridge.
- npm stable `@paperclipai/mcp-server@2026.916.1` matches the pinned Paperclip release. Slice 1 allows only identity plus project/issue read, issue create/update, comment read/write; it excludes goal/project creation, approvals, runtime control, connections, and the arbitrary API escape hatch.
- The pinned server attributes existing-issue mutations to a heartbeat run. A standard claimed agent key without a valid `X-Paperclip-Run-Id` can read and create permitted issues, but update/comment requests fail closed; the official MCP adds that header only when `PAPERCLIP_RUN_ID` is present. Nix's Docker recovery test therefore exercises issue creation first, establishes a supported issue-scoped run, then proves update/comment through the same bounded MCP with that run context. A Paperclip-triggered live gateway run remains part of production acceptance.
- Authenticated/private mode rejects unapproved `Host` values before routes execute. Because Hermes reaches Paperclip as `http://paperclip:3100` on the isolated Docker network, Nix supplies and validates the supported runtime setting `PAPERCLIP_ALLOWED_HOSTNAMES=paperclip`. This admits a hostname, not a network path; no Paperclip port is published beyond host loopback.
- The supported external-agent flow is invite acceptance, board approval, then one-time `claim-api-key`. The claim cannot be replayed. Nix preflights the profile and couples claim, mode-`0600` write, `fsync`, atomic rename, and authenticated identity verification in one container operation. If the server consumed a claim but the key cannot be recovered, the orphaned credential must be revoked/removed through supported Paperclip administration and a new invitation issued.
- The [OpenCode adapter](https://docs.paperclip.ing/reference/adapters/opencode/) runs `opencode run --format json`, supports provider/model selection, and resumes sessions when `cwd` matches.
- Paperclip uses PostgreSQL and supports a local Docker PostgreSQL mode in its [database documentation](https://docs.paperclip.ing/reference/deploy/database/). The single-VPS choice is ours; it is not a claim that a local database is more durable than managed PostgreSQL.
- The exact release's [Docker guide](https://github.com/PaperclipAI/paperclip/blob/v2026.916.1/doc/DOCKER.md) supports an external PostgreSQL 17 Compose stack, persists all non-database Paperclip state under `/paperclip`, and uses `PAPERCLIP_PUBLIC_URL` as the canonical auth/invite origin. Its official Docker onboarding smoke provisions configuration with `paperclipai onboard` before starting the server and then exercises real signup/bootstrap-invite acceptance.
- `paperclipai auth bootstrap-ceo` requires `/paperclip/instances/default/config.json`. In this release, the missing-config branch prints `Run paperclip onboard first` but returns exit status zero, so Nix verifies a real active invite through `GET /api/invites/:token` rather than trusting the command status.
- Non-interactive `onboard --yes` forces trusted loopback unless a private `--bind` preset is supplied; `--bind lan` writes `authenticated/private`. Nix retains the official Quickstart onboarding path in a bounded pseudo-terminal so environment-aware defaults produce `authenticated/private`, external PostgreSQL, the explicit Tailscale HTTPS URL, local-disk storage, and local-encrypted secrets. It validates every resulting field before server startup.
- The official PostgreSQL image grants superuser status to `POSTGRES_USER`. Nix therefore keeps the image's `postgres` bootstrap administrator separate and creates the application-facing `paperclip` database owner with `NOSUPERUSER`, `NOCREATEDB`, and `NOCREATEROLE` during first initialization.
- Required Slice 0 variables are `DATABASE_URL`, `BETTER_AUTH_SECRET`, and `PAPERCLIP_TOOL_ACTION_SIGNING_SECRET`, plus explicit deployment and canonical URL settings. `PAPERCLIP_HOME=/paperclip` is a persistent named volume. The tool-action secret has no fallback.
- On an empty external database, the server bootstraps the bundled Drizzle migrations. On an upgraded database, a non-interactive process applies pending migrations; Slice 0 makes this deliberate with `PAPERCLIP_MIGRATION_AUTO_APPLY=true` and always backs up before upgrade. In the pinned source, a non-empty PostgreSQL schema without the expected Drizzle migration journal enters the auto-migration path, is inspected, and is rejected before any migrations are applied. Nix keeps a separate read-only table/journal preflight as defense in depth: the documented deploy, upgrade, restart, and restore workflows fail earlier with a clearer operator error. A direct Compose startup or engine-managed container restart does not necessarily run the Nix preflight, but the pinned upstream guard still fails closed before mutation. Future releases still require migration-source review.
- Anonymous `GET /api/health` is intentionally redacted in authenticated mode, probes PostgreSQL with `SELECT 1`, returns HTTP 503 with `database_unreachable` when that probe fails, and reports `status: ok` only after startup recovery reaches ready.
- Tailnet exposure uses `authenticated/private`, which still requires login and supports a browser-first ownership claim for the first authenticated session. [ADR 0005](decisions/0005-tailnet-private-ingress.md) records this boundary. External PostgreSQL remains the Nix deployment choice, and signup is disabled immediately after the claim.
- The supported company, issue, attachment, secrets, and environment-probe routes are sufficient for realistic backup/restore fixtures. Attachment bytes live below `/paperclip`; their metadata and company/issue relationships live in PostgreSQL. Secret creation through the board API stores `local_encrypted` ciphertext, and normal reads expose metadata only. A board-authorized environment probe resolves a bound secret server-side and records a success access event without returning its value. Slice 0 uses that supported surface to prove restored ciphertext still decrypts with the restored master key without introducing an agent or logging plaintext.
- Paperclip [company exports](https://docs.paperclip.ing/how-to/back-up-and-restore-a-company/) deliberately omit approvals, cost events, activity history, secret values, and machine-specific state. They supplement rather than replace database and volume backups.

### Hermes Agent

- The current stable release is [Hermes Agent v2026.9.24](https://github.com/NousResearch/hermes-agent/releases/tag/v2026.9.24) / `v0.21.5` (2026-09-24), commit `f97608f178d1ffeca59860195ab7da295f7c8e5f`. Its Docker Hub multi-architecture digest is `sha256:fca358f12efd65bfaaca05884166f15c0e2788375ca30d77061ac1ebc96452b7`; linux/amd64 resolves to `sha256:2fd023efbb8d3d2b0ce1a73d028b07370cff34f567cfe0e999553e8c327ea283`. Releases after the Slice 1 pin include gateway singleton locking, profile/multiplex lifecycle fixes, centralized Telegram admission, and broad configuration/tool/runtime churn. There is no published must-upgrade advisory for the pinned release. Keep `v2026.9.14` through Slice 1 live acceptance and requalify the newer release separately.
- The Slice 1 pinned release is [Hermes Agent v2026.9.14](https://github.com/NousResearch/hermes-agent/releases/tag/v2026.9.14), source commit `345cd2b057a452236de401d3534b8502a7465e8d`. The official multi-architecture image is pinned above; its linux/amd64 manifest resolved to `sha256:1f983df4d778d46b3c3892d7598c9d57291430a6e35936ebc371ae1e5766699a`.
- The official Docker image uses s6 supervision, persists the complete Hermes home at `/opt/data`, includes Node/npm for stdio MCP servers, and supports `HERMES_GATEWAY_BOOTSTRAP_STATE=running` for restart persistence. The pinned runtime also hydrates values from the persistent profile `.env` after process startup. Nix therefore treats Telegram credentials and admission controls as external-only: its entrypoint durably strips stale copies from `/opt/data/.env` before delegating to the upstream dispatcher, then the root-owned mode marker either clears the external token or requires it. Nix does not add the optional dashboard or publish a Hermes port.
- The pinned image's project `.npmrc` enforces `min-release-age=14`. npm reports `@paperclipai/mcp-server@2026.916.1` was published at `2026-09-21T21:14:09.037Z`; on 2026-10-03 it is still younger than the policy threshold. Nix therefore retains `--min-release-age=0` only on this exact version-pinned MCP invocation and regression-tests its discovered tool surface; it does not disable the image policy globally or permit an unpinned package. Remove the override after the package passes the threshold and validation remains green.
- [Profiles](https://hermes-agent.nousresearch.com/docs/user-guide/profiles) isolate configuration, secrets, memory, sessions, skills, and state. Upstream explicitly warns against two agent processes writing the same profile.
- The [messaging gateway](https://hermes-agent.nousresearch.com/docs/user-guide/messaging) natively supports Telegram polling, persistent platform sessions, background delivery, numeric allowlists, and `unauthorized_dm_behavior: ignore`. `group_policy` is not a recognized setting in the pinned release and was removed. Slice 1 uses `TELEGRAM_ALLOWED_USERS`, `guest_mode: false`, `allow_bots: none`, and a non-empty `allowed_chats` gate containing only Lior's positive user ID; Telegram group/forum IDs are negative. Both global and Telegram allow-all flags remain false. Fixture tests exercise the pinned adapter/auth logic for Lior DM, unknown DM, Lior-in-group, forum/topic, and bot-sender cases. Slice 3 must deliberately replace the DM-only chat gate when it introduces approved topic routes.
- The [programmatic API](https://hermes-agent.nousresearch.com/docs/developer-guide/programmatic-integration) provides authenticated Runs endpoints and SSE events used by Paperclip. `API_SERVER_KEY` is mandatory when enabled. Binding `0.0.0.0:8642` inside the container is required for bridge access; Compose publishes no host port.
- The pinned release resolves platform-specific toolsets for `cli`, `telegram`, and `api_server`; explicit lists replace broad presets. Nix assigns all three lanes exactly `file`, `memory`, `session_search`, and `paperclip`, while globally disabling mutable skills, terminal, code execution, browser/web, connectors, delegation, cron, and computer-use. Runtime discovery requires exactly the native concrete tools `memory`, `patch`, `read_file`, `search_files`, `session_search`, and `write_file`, plus exactly nine Paperclip MCP operations; any additional concrete tool fails validation. Tool Search may expose its scoped `tool_search`, `tool_describe`, and `tool_call` bridge, but its underlying catalog is checked separately and contains only the approved tools. The pinned runtime's actual file entry points are exercised with `HERMES_WRITE_SAFE_ROOT=/opt/data/memories`: `.env` and `auth.json` reads fail, broad searches omit credential canaries, writes and patches outside the safe root or through symlink escapes fail, and the image-provided grilling guidance remains readable but immutable through the model-visible tools.
- In `v2026.9.14`, authenticated `GET /v1/toolsets` accurately reports enabled configurable built-in API-server toolsets but omits native MCP alias rows. Nix checks that endpoint and also runs the pinned runtime's MCP discovery plus raw-tool introspection; configuration labels alone are not accepted as proof of the boundary.
- [Multi-profile gateways](https://hermes-agent.nousresearch.com/docs/user-guide/multi-profile-gateways) support `gateway.multiplex_profiles` and `gateway.profile_routes`, including Telegram chat/thread matching. Slice 1 keeps multiplexing off and uses the default profile as Chief; a pinned-image regression test proves representative future topic routes select separate profile names.
- Hermes' [MCP configuration](https://hermes-agent.nousresearch.com/docs/reference/mcp-config-reference) supports stdio servers, explicit tool filtering, and `${PAPERCLIP_API_KEY}` (also `${env:PAPERCLIP_API_KEY}`) references resolved from the active profile environment. Nix keeps the values in the persistent profile's mode-`0600` `.env`, not in Git-controlled YAML.
- Hermes supports ChatGPT/Codex subscription authentication through `hermes auth add openai-codex --type oauth`; the default device-code flow stores refreshable credentials in `/opt/data/auth.json`. Nix selects provider `openai-codex` and model `gpt-5.4` in replaceable profile configuration and does not require an API key.
- The pinned image includes official `grill-me` guidance (version 2.0.0, Matt Pocock-style grilling) at `/opt/hermes/optional-skills/software-development/grill-me/SKILL.md`. Slice 1 reads that pinned file directly as immutable reference guidance; it does not install a mutable profile skill or expose skill-management tools. Full Project Inception is deferred.

### Telegram

The [Telegram Bot API](https://core.telegram.org/bots/api) offers mutually exclusive polling and webhook delivery. Hermes owns polling and outbound messages. Paperclip's experimental connector instead requires a Telegram webhook and a publicly reachable webhook origin on a supported public port, is one-bot/one-agent oriented, and does not supply Hermes SOUL/memory/skills/profile routing. It therefore does not meet the tailnet-only persistent-employee requirement and remains disabled; Nix must not add a second Telegram receiver.

### Todoist

The [Todoist developer platform](https://developer.todoist.com/) now presents one API, official SDKs/CLI/MCP, and webhooks. The [API v1 reference](https://developer.todoist.com/api/v1/) documents opaque string IDs, cursor pagination, JSON errors, webhook HMAC verification, and redelivery with the same delivery ID.

### n8n

- The stable tag on 2026-09-22 was [n8n 2.39.10](https://github.com/n8n-io/n8n/releases/tag/n8n%402.39.10).
- n8n supports PostgreSQL 17 and 18 (plus compatibility support for 16) in its [official database guide](https://github.com/n8n-io/n8n-docs/blob/main/docs/deploy/host-n8n/configure-n8n/choose-n8ns-database.md).
- n8n uses `N8N_ENCRYPTION_KEY` to protect stored credentials; the official [encryption-key guide](https://github.com/n8n-io/n8n-docs/blob/main/docs/deploy/host-n8n/configure-n8n/basic-configuration/configuration-examples/set-a-custom-encryption-key.md) makes that key part of the restore contract.

### Infrastructure

- Docker documents [single-server production Compose](https://docs.docker.com/compose/how-tos/production/) and [per-service Compose secrets](https://docs.docker.com/compose/how-tos/use-secrets/).
- PostgreSQL documents consistent logical exports with [`pg_dump`](https://www.postgresql.org/docs/17/app-pgdump.html) and stresses regular, verified backups in its [backup guide](https://www.postgresql.org/docs/17/backup.html).
- GitHub recommends minimum GitHub App permissions in [Choosing permissions for a GitHub App](https://docs.github.com/en/apps/creating-github-apps/registering-a-github-app/choosing-permissions-for-a-github-app).
- Tailscale documents [`tailscale set --hostname`](https://tailscale.com/kb/1098/machine-names), [MagicDNS](https://tailscale.com/docs/features/magicdns), and [`tailscale serve`](https://tailscale.com/docs/reference/tailscale-cli/serve). `serve status --json` returns raw node-level configuration including `TCP`, `Web`, `Services`, `AllowFunnel`, and `Foreground`; `serve reset` clears the whole node and is therefore unsafe on this shared host. The supported `--https=443 --set-path=/` form targets Nix's one handler but also depends on the shared TCP `443` HTTPS listener. Nix therefore owns that listener, the root handler, and absence of a Funnel entry for the endpoint. It preflights listener and foreground conflicts, applies the handler in place, verifies its exact target, and compares before/after state outside those owned fields. The comparison detects unexpected mutation but cannot make the upstream CLI transaction atomic. Serve is tailnet-only and subject to tailnet access controls; Funnel remains forbidden for Paperclip. Tailnet HTTPS may require an administrator to enable MagicDNS/HTTPS and acknowledge certificate-transparency disclosure of machine and tailnet names in the [DNS settings flow](https://tailscale.com/docs/how-to/set-up-https-certificates).
- Tailscale's [operator-user setting](https://tailscale.com/docs/reference/troubleshooting/linux/linux-operator-permission) permits the `nix` user to operate the CLI without broadening the Compose privilege model.
- rclone's [Google Drive backend](https://rclone.org/drive/) supports interactive OAuth and file transfers. Its shared Google client ID is being retired during 2026, so live setup uses Lior's own Desktop OAuth client ID and the `drive.file` scope. That scope limits the client to objects it creates or that Lior explicitly opens with it; Nix therefore uses an app-created backup root and records its `root_folder_id`. A replacement host must use the same OAuth client/config to retain access. The exact rclone config contains refresh credentials, remains outside Git and outside the Drive it protects, and is escrowed separately under age encryption. Existing backup objects created through another client or broader grant must be downloaded and verified, then re-uploaded through the narrowed client before that old grant is revoked.

## Known overlaps that are intentionally not used

- Paperclip now has experimental chat connectors, including Telegram. The locked architecture puts conversation in Hermes, so these stay disabled in V0.
- Paperclip and Hermes both contain task/kanban-like features. Paperclip alone is authoritative; Hermes-native kanban is not used for company work.
- Todoist offers MCP and a CLI. The V0 projection must be deterministic and policy-filtered, so n8n owns the eventual sync rather than giving every agent direct Todoist write access.
- Paperclip and n8n have broad plugin/connector ecosystems. V0 uses only integrations required by an accepted slice.
